About this PostgreSQL config generator

PostgreSQL ships with conservative defaults that assume a shared machine with very little memory — shared_buffers of 128 MB, work_mem of 4 MB, and planner cost constants tuned for spinning disks. On a modern VPS or dedicated database server those defaults leave most of your RAM unused and force queries to spill sorts and hashes to disk. This tool generates a tuned postgresql.conf snippet from six inputs: total RAM, CPU cores, storage type, PostgreSQL version, workload type, and expected maximum connections.

It ports the well-known PGTune formulas: shared_buffers at 25% of RAM (1/16 for desktop use), effective_cache_size at 75% of RAM, work_mem derived from available memory divided by connection count and a parallelism factor, maintenance_work_mem at 1/16 of RAM capped at 2 GB, wal_buffers at 3% of shared_buffers capped at 16 MB, workload-specific min_wal_size / max_wal_size, checkpoint_completion_target of 0.9, default_statistics_target of 100 (500 for data warehouses), random_page_cost of 1.1 for SSD/NVMe or 4 for HDD, effective_io_concurrency, and parallel worker settings when you have 4 or more cores. It is useful for developers deploying Postgres to a Vultr VPS, DevOps engineers sizing a managed database, and anyone comparing their current config against a known-good baseline.

Start from your hardware: set shared_buffers to about 25% of RAM, effective_cache_size to about 75% of RAM, and derive work_mem from (RAM minus shared_buffers) divided by (max_connections times 3) and a parallelism factor. Then adjust for your workload type and storage, restart PostgreSQL for the settings that need it, and re-check pg_stat_statements and temp file counts under real load. For web, OLTP, mixed and data-warehouse workloads, shared_buffers is set to roughly 25% of total RAM. On a desktop or development machine it is much smaller, around 1/16 of RAM. Going far above 25% rarely helps because PostgreSQL also relies on the operating system page cache, which effective_cache_size describes to the planner. On a 4 GB server that means about 1 GB of shared_buffers.

work_mem is per sort or hash operation per connection, so it is derived from available memory and connection count: (RAM minus shared_buffers) divided by (max_connections times 3), then divided by the parallel workers per gather and a workload divisor (1 for web and OLTP, 2 for mixed and data warehouse, 6 for desktop). Setting it too high can exhaust RAM when many connections sort at once, so keep max_connections realistic and use a connection pooler.
On a small VPS the priorities are: shared_buffers near 25% of RAM, effective_cache_size near 75%, a modest work_mem so concurrent queries do not exhaust memory, random_page_cost of 1.1 because VPS storage is SSD or NVMe, effective_io_concurrency around 200, and checkpoint_completion_target of 0.9 to smooth write spikes.
